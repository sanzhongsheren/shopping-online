## 一、XP（极限编程）开发方法

### 1.1 XP概述

极限编程（eXtreme Programming, XP）是敏捷开发中最具代表性的方法之一，由 Kent Beck 在1996年提出。XP将已经被验证的最佳工程实践"推向极致"，强调开发速度与代码质量并重。

### 1.2 XP核心价值观

| 价值观 | 说明 |
|--------|------|
| 沟通（Communication） | 团队成员之间、与客户之间保持高频沟通，降低信息损耗 |
| 简单（Simplicity） | 只做当前需要的，不做复杂的前瞻设计（YAGNI原则） |
| 反馈（Feedback） | 通过测试、持续集成、客户评审等机制获取快速反馈 |
| 勇气（Courage） | 敢于重构已有代码、敢于丢弃过时的设计、敢于面对困难 |
| 尊重（Respect） | 团队成员相互尊重，认可每个人的贡献 |

### 1.3 XP核心实践

| 实践 | 说明 | 在本项目中的应用 |
|------|------|----------------|
| 完整团队 | 客户与开发团队在同一地点工作 | 小组成员在同一教室/在线协作 |
| 计划游戏 | 用户故事驱动，客户确定优先级 | 使用功能模块列表替代用户故事 |
| 小版本发布 | 每个发布版本尽可能小 | 每个Sprint交付一个可用功能模块 |
| 用户故事 | 用自然语言描述功能需求 | 需求规格说明书中有详细的功能需求描述 |
| 简单设计 | 保持设计尽可能简单 | 三层架构（路由-控制器-模型），无过度设计 |
| 结对编程 | 两人共用一台计算机编程 | 后端两人可结对开发核心模块 |
| 测试驱动开发（TDD） | 先写测试再写代码 | 关键接口使用Postman手动测试验证 |
| 重构 | 持续改进代码结构而不改变行为 | 每次Sprint回顾后对代码进行重构优化 |
| 持续集成 | 频繁集成代码变更 | 使用Git分支管理，功能完成后合并 |
| 编码标准 | 全组统一代码风格 | 统一使用ESLint规则和项目命名规范 |
| 集体代码所有权 | 任何人都可以修改任何代码 | 全组成员都可以提交修改 |
| 可持续节奏 | 保持稳定工作节奏，避免加班 | 课程学期内按周分配合理工作量 |

### 1.4 本项目中XP实践总结

本项目虽未完全采用XP方法论，但在以下方面吸收了XP的核心理念：
- **简单设计**：Express三层架构简单直接，不过度抽象
- **重构**：每完成一个功能模块后进行代码审视和重构
- **编码标准**：前后端代码统一风格

## 二、DevOps

### 2.1 DevOps概述

DevOps 是 Development（开发）和 Operations（运维）的组合词，代表一组将软件开发与IT运维相结合的文化实践、工具和方法论。其目标是缩短系统开发生命周期，同时提供高质量的持续交付。

### 2.2 DevOps核心实践

| 实践 | 说明 |
|------|------|
| 持续集成（CI） | 代码频繁合并到主干，自动化构建和测试 |
| 持续交付（CD） | 确保代码随时处于可部署状态 |
| 基础设施即代码（IaC） | 使用代码管理和配置基础设施 |
| 监控与日志 | 持续监控应用和基础设施运行状况 |
| 微服务 | 将大型系统拆分为小型独立服务 |

### 2.3 DevOps工具链

| 阶段 | 工具 | 本项目使用 |
|------|------|-----------|
| 计划 | Jira, Trello | 腾讯文档 + Project Libre |
| 编码 | VS Code, IntelliJ | VS Code |
| 构建 | npm, Maven, Docker | npm |
| 测试 | JUnit, Selenium, Postman | Postman |
| 部署 | Docker, Kubernetes, Jenkins | 本地运行 + 手动部署 |
| 监控 | Prometheus, Grafana | 控制台日志 |

### 2.4 对本课程的适用性评估

由于本课程项目为小型教学项目，不涉及生产环境部署和大规模运维，DevOps的完整实践在本项目中受限制。但**持续集成**的理念被项目采纳——通过Git分支管理和小步提交实现代码的持续合并。

## 三、项目活动图与关键路径

### 3.1 工作活动分解（WBS）

根据商品网上交易系统的开发需求，对项目工作进行活动分解：

| 活动编号 | 活动名称 | 前置活动 | 预估工期（天） |
|----------|----------|----------|---------------|
| A | 需求分析与文档编写 | - | 5 |
| B | 数据库设计与建表 | A | 3 |
| C | 用户管理模块开发 | B | 4 |
| D | 商品管理模块开发 | B | 5 |
| E | 购物车模块开发 | C | 3 |
| F | 订单管理模块开发 | C, D | 5 |
| G | 审核管理模块开发 | C | 3 |
| H | 留言与收藏模块开发 | C | 3 |
| I | 前端页面开发 | D | 6 |
| J | 前后端联调与测试 | E, F, G, H, I | 5 |
| K | 文档完善与提交 | J | 3 |

### 3.2 项目活动网络图

```
    A(需求分析,5天)
     ↓
    B(数据库设计,3天)
     ↓
    ┌────────────┬──────────────┐
    ↓            ↓              ↓
   C(用户管理,4天)  D(商品管理,5天)   G(审核管理,3天)
    │            │              │
    ├───┬────────┤              │
    ↓   ↓        ↓              │
   E   F        I(前端,6天)     │
  (购物车,3天) (订单,5天)       │
    │   │        │              │
    └───┴────────┴──────────────┘
              ↓
          J(联调测试,5天)
              ↓
          K(文档完善,3天)
```

### 3.3 关键路径分析

对各路径的时间累加计算：

- **路径1**：A → B → C → E → J → K = 5+3+4+3+5+3 = **23天**
- **路径2**：A → B → C → F → J → K = 5+3+4+5+5+3 = **25天**
- **路径3**：A → B → C → G → J → K = 5+3+4+3+5+3 = 23天
- **路径4**：A → B → C → H → J → K = 5+3+4+3+5+3 = 23天
- **路径5**：A → B → D → F → J → K = 5+3+5+5+5+3 = **26天**
- **路径6**：A → B → D → I → J → K = 5+3+5+6+5+3 = **27天**

### 3.4 关键路径结果

**关键路径为：A → B → D → I → J → K**

即：需求分析(5天) → 数据库设计(3天) → 商品管理模块(5天) → 前端页面开发(6天) → 联调测试(5天) → 文档完善(3天)

**关键路径总长度：27天**

这意味着如果每个工作日都有进度推进，项目最少需要27个工作日完成。考虑到课程学期内的时间安排（约12-15周，每周约2个有效工作日），项目总体工期约为13-14周，留有一定缓冲时间。

## 四、实验小结

本实验深入学习了XP开发方法和DevOps理念，结合本项目特点进行了适用性分析。同时完成了项目工作的活动分解和活动图绘制，通过关键路径分析确定了项目最短工期为27个工作日，识别了关键活动链——需求分析、数据库设计、商品管理、前端开发、联调测试、文档完善是决定项目进度的核心环节，需要在执行中重点跟踪。
