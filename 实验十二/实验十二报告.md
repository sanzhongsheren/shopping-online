## 二、依赖注入（Dependency Injection）

### 2.1 依赖注入概述

依赖注入（DI）是一种设计模式，其核心思想是：**对象不自己创建依赖，而是由外部注入所需依赖**。这实现了控制反转（IoC）。

**传统方式（硬编码依赖）**：
```js
// 传统：Controller自己引入Model
const Order = require("../models/order");
```

**依赖注入方式**：
```js
// DI：依赖由外部传入
function createOrderController(orderModel, responseUtil) {
  return {
    createOrder: async (req, res) => {
      const result = await orderModel.createOrder(...);
      responseUtil.success(res, result);
    }
  };
}
```

### 2.2 依赖注入的优点

| 优点 | 说明 |
|------|------|
| **解耦** | 高层模块不依赖低层模块的具体实现，只依赖接口 |
| **可测试性** | 单元测试时可方便地注入Mock对象 |
| **可替换性** | 更换依赖的实现（如更换数据库），业务代码无需修改 |
| **可配置性** | 依赖关系可以在配置文件中管理 |

### 2.3 依赖注入的三种形式

| 形式 | 说明 | 代码示例 |
|------|------|----------|
| **构造函数注入** | 通过构造函数参数传入依赖 | `class OrderController { constructor(orderModel) {...} }` |
| **Setter注入** | 通过setter方法设置依赖 | `controller.setOrderModel(model)` |
| **接口注入** | 通过接口注入依赖（强类型语言） | Java的`@Inject`, `@Autowired` |

### 2.4 本项目对DI的应用分析

本项目目前使用的是 Node.js 的 `require()` 模块系统，这是 **服务定位器模式** 的一种简单形式，而非完整的依赖注入。实际上：

**当前做法**（require直接引入）：
```js
const Order = require("../models/order");
const { success, error } = require("../utils/response");
```

**如果采用DI（可选优化方向）**：
```js
// 1. 定义接口（契约）
// 2. 在app.js中组装依赖：
app.set('orderModel', require('./models/order'));
app.set('responseUtils', require('./utils/response'));

// 3. 在控制器中获取：
const orderModel = req.app.get('orderModel');
```

**评估结论**：对于本课程项目规模，目前使用 `require()` 的直接依赖引入已经足够清晰。若项目未来扩展到需要Mock测试或多数据库切换场景，可考虑引入DI容器。

### 2.5 DI最佳实践总结

1. **小型项目**：直接使用语言内置的模块系统（如Node.js的require）
2. **中型项目**：可考虑轻量DI库（如 Awilix、InversifyJS）或使用Express的 `app.set/get`
3. **大型项目**：使用专业DI框架（如Spring的@Autowired、Nest.js的@Injectable）

## 三、面向对象设计原则论述

### 3.1 六大设计原则概述

> 小组对项目中应用的六大设计原则进行了详细论述，完整内容见 [docs/设计原则论述.md](../docs/设计原则论述.md)。

| 设计原则 | 核心思想 | 本项目关键实践 |
|----------|----------|---------------|
| **单一职责原则(SRP)** | 一个类/模块只做一件事 | `response.js` 专一负责响应格式；认证与授权中间件分离 |
| **开闭原则(OCP)** | 对扩展开放，对修改关闭 | Express中间件链无限扩展能力；`authorizeRoles(...)` 支持任意新角色 |
| **里氏代换原则(LSP)** | 子类型应能完全替代父类型 | 中间件共享`(req,res,next)=>void`签名，路由中可任意替换 |
| **迪米特法则(LoD)** | 只和直接朋友通信 | 控制器只依赖模型+响应工具；三层架构每层依赖最小化 |
| **依赖倒转原则(DIP)** | 依赖抽象而非具体实现 | 控制器依赖模型函数接口而非数据库实现；分层架构天然倒置依赖 |
| **合成复用原则(CARP)** | 优先使用组合而非继承 | 中间件链水平组合行为；模型零继承独立复用；HTTP方法组合`_request` |

### 3.2 结合项目的具体应用说明

#### 里氏代换原则（LSP）在中间件中的应用

项目的认证中间件和授权中间件都具有统一的函数签名 `(req, res, next) => void`，这使得它们在Express中间件链中可以任意替换和排列：

```js
// 签名一致 → 可替换
exports.authenticate = (req, res, next) => { ... };
exports.authorizeRoles = (...roles) => (req, res, next) => { ... };

// 路由中任意组合，行为正确
router.post("/", authenticate, authorizeRoles("buyer"), createOrder);
router.put("/:id/ship", authenticate, authorizeRoles("seller"), shipOrder);
```

#### 单一职责原则（SRP）在三层架构中的体现

| 层 | 职责 | 唯一变化原因 |
|----|------|-------------|
| 路由层 | URL到处理函数的映射 | API端点变更 |
| 控制器层 | 业务逻辑编排 | 业务流程变更 |
| 模型层 | 数据CRUD操作 | 数据库结构变更 |

#### 开闭原则（OCP）在功能扩展中的体现

```js
// 已有代码无需修改（对修改关闭）
app.use("/api/products", require("./routes/products"));
app.use("/api/orders", require("./routes/orders"));

// 新增功能模块只需添加一行（对扩展开放）
app.use("/api/coupons", require("./routes/coupons"));  // 新增优惠券模块
```
